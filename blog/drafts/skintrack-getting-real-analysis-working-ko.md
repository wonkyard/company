# 버그 네 개가 겹쳐 쌓여 있었습니다 — 안드로이드에서 피부 분석 API 붙이기

> "셀카 한 장 찍으면 내 피부 상태를 시간순으로 추적해 주는" 앱을 오래 만들고 싶었습니다. Perfect Corp에서 YouCam AI Skin Analysis API의 무료 유닛을 제공해 줘서, 드디어 만들었습니다. skintrack 시리즈 1편은 화려하지 않은 부분입니다. 실제 분석 호출이 계속 실패했는데, 알고 보니 서로 다른 버그 네 개가 겹쳐 쌓여 있었습니다. 2편은 이걸 제품으로 어디까지 끌고 갈지에 대한 이야기입니다.

## 먼저 스폰서 고지

Perfect Corp이 먼저 연락을 줬고, 이 프로젝트에 쓸 API 유닛을 무료로 제공했습니다(대략 500유닛, 피부 스캔으로 치면 80~125회 정도). 이게 이 앱을 "언젠가"가 아니라 지금 만들게 된 유일한 이유입니다. 제품 관련 결정에는 아무 영향도 주지 않았고, 이 글은 그 API에 대한 리뷰가 아닙니다. 굳이 밝히는 건 그게 정직한 일이기 때문이고, 유닛 예산이 뒤에 이야기 전개에 실제로 등장하기 때문입니다. 테스트 호출을 마구 날릴 수가 없었거든요.

이 정도로 정리하고, 유닛도 받았으니 실제로 만들어 보겠습니다.

## 이 앱이 뭔지

개인용 안드로이드 앱입니다. 제 폰에 사이드로드만 했고 스토어 출시는 없습니다. 셀카를 찍으면 피부 분석을 돌리고, 항목별 점수를 로컬에 저장한 다음, 시간에 따른 추이를 보여줍니다. 루틴을 바꿨을 때 그게 실제로 뭔가 효과가 있는지 없는지 판단할 수 있게요.

(이미지-자리표시자: 앱 홈 화면 — "셀카 찍기" / 최근 결과)

원래 설계(시작하기 전날 잡아둔 것)는 빌드리스 웹 앱에, API 키를 숨기기 위한 선택적 서버리스 프록시를 두는 구조였습니다. 그런데 이걸 네이티브 안드로이드 앱으로 다시 잡으니 그 복잡도의 대부분이 증발했습니다. 네이티브 HTTP에는 브라우저 오리진이 없으니 CORS가 애초에 적용되지 않고, 프록시 계층이 통째로 사라집니다. 앱이 `Bearer` 키로 서버-대-서버 엔드포인트를 직접 호출합니다.

최종적으로 **프레임워크 없는 `core/`를 Capacitor로 감싸는** 구조로 정했습니다.

- `core/` — 순수 ES 모듈, Capacitor import 0개. API 로직, 메트릭 설정, 추이 계산이 전부 여기 있습니다. 플랫폼 기능(HTTP, 저장소, 카메라, 시크릿)은 주입받습니다.
- `platform/` — 그 기능들을 제공하는 Capacitor 어댑터.
- `src/screens/` — 순수 바닐라 JS 뷰.

버린 선택지: 네이티브 Kotlin(나중에 웹 버전을 만들 때 재사용 0), Flutter / React Native(툴체인이 삭을 위험, 전체 재작성), 그냥 PWA(WebView 오리진이 CORS와 프록시를 다시 불러옴). 이렇게 쪼갠 이유는 `core/`가 지금은 Node에서 테스트용으로 그대로 돌아가고, 나중에 브라우저에서도 돌 수 있게 하기 위해서입니다.

**v0.1**은 뼈대였습니다. V2 스펙에 맞춰 짠 전체 API 어댑터, 키를 붙여넣는 설정 화면(안드로이드 Keystore로 암호화), 그리고 기본으로 켜져 있는 목(mock) 어댑터 — 덕분에 키 없이도 앱이 돌고 비용이 0입니다. 테스트 50/50 통과.

**v0.2**는 v0.1이 실제 폰을 만나서 진 부분입니다. 제 "번들러 없이" 트릭 — Capacitor 플러그인 파일을 `www/vendor/`로 복사하고 import map으로 연결하는 것 — 은 데스크톱 브라우저에서는 되는데 **안드로이드 WebView에서는 깨집니다.** 플러그인 dist 파일이 자기 내부에서 중첩된 지연 `import()`를 하기 때문입니다. "셀카 찍기"를 실제로 처음 눌렀을 때:

```
failed to fetch dynamically imported module .../vendor/@capacitor/...
```

키를 저장한 상태에서 실제 분석을 돌리면? 아무 일도 안 일어나고, 에러도 안 뜹니다. HTTP 경로가 똑같이 깨진 모듈 로드를 거쳤고, 에러를 표시할 표면 자체가 없었으니까요. 목만 됐던 건 목이 `@capacitor/*`도 네트워크도 건드리지 않기 때문이었습니다.

그래서 빌드리스 도그마를 버리고 Vite를 도입했습니다 — Capacitor 표준 빌드입니다. `core/`는 프레임워크 없는 상태 그대로, 패키징만 바뀌었습니다. v0.2에서는 카메라와 갤러리를 별개의 두 액션으로 나눴고, 모든 에러를 화면에 보이게 만들었고, Diagnostics 화면(복사 가능, 키는 마스킹)을 추가했습니다. 테스트 66/66.

여기까지 오니 드디어 유닛을 실제로 쓰는 진짜 분석을 돌려볼 수 있는 빌드가 나왔습니다. 그리고 여기서부터 재밌어집니다.

## 디버깅 사가: 버그 네 개, 증상 하나

빌드를 설치하고, 실제 사진을 고르고, 분석을 눌렀습니다. 가장 첫 네트워크 호출에서 766ms 만에 실패했습니다:

```
POST https://yce-api-01.makeupar.com/s2s/v2.0/file → 400
{"status":400,"error":"file_size is required but wasn't included in your request.","error_code":"InvalidParameters"}
```

문제는, 코드가 `file_size`를 *보낸다*는 겁니다. 확인했습니다. `_buildFileBody()`가 만드는 건 정확히 이겁니다:

```json
{"files":[{"content_type":"image/jpeg","file_name":"selfie.jpg","file_size":131072}]}
```

그래서 API 키를 들고 똑같은 `/file` 엔드포인트를 그냥 `curl`로 쳐봤습니다 — `/file` 호출은 메타데이터만 등록하고 유닛을 안 쓰기 때문에 공짜 탐침이었습니다. curl에서는 그 똑같은 바디가 **HTTP 200**을 돌려줍니다. 요청 모양은 맞았습니다. 앱이 `core`와 실제 전송 사이 어딘가에서 요청을 뭉개고 있었습니다.

### 버그 1 — 안드로이드 네이티브 HTTP는 미리 문자열화된 JSON 문자열을 안 보냅니다

`core`는 바디를 만들고 `JSON.stringify(...)`를 하기 때문에, 플랫폼 계층은 `Content-Type: application/json`이 붙은 *문자열*을 받습니다. 웹 / Node에서는 이게 정확히 맞습니다. 그런데 안드로이드의 `CapacitorHttp`는 JS 객체를 자기가 직렬화하고, `application/json`에 대해 미리 문자열화된 raw 문자열을 그대로 전송하지 않습니다 — 재인코딩하거나 버립니다. 그러면 서버는 읽을 수 있는 필드가 하나도 없으니, 첫 번째 필수 필드 이름을 댑니다: `file_size`. 400은 진짜였습니다. 다만 원인에서 세 계층 떨어진 증상을 가리키고 있었을 뿐입니다.

수정은 전송 어댑터 안에 둡니다 — `core`는 fetch와 Node가 그대로 처리하는 스펙에 맞는 문자열을 계속 뱉습니다:

```js
const ct = (headers['Content-Type'] ?? headers['content-type'] ?? '').toLowerCase();
if (typeof body === 'string' && ct.includes('json')) {
  // core emits a JSON *string* (correct for fetch / Node). Android CapacitorHttp
  // does not transmit a pre-stringified application/json string faithfully — it
  // serialises JS objects itself and drops/re-encodes a raw string, so YouCam
  // sees no fields and returns 400 "file_size is required". Parse it back here.
  try { options.data = JSON.parse(body); } catch { options.data = body; }
} else {
  options.data = body;
}
```

이 와중에도 모든 테스트 스위트는 66/66으로 통과했습니다. 전부 `core` 이음새에 가짜 HTTP 클라이언트를 주입하고 `platform/http-capacitor.js`는 한 번도 안 건드리기 때문입니다. 그게 진짜 구멍이었습니다 — 전송 어댑터를 테스트하는 게 아무것도 없었습니다. 어댑터가 주입된 transport를 받도록 리팩터링해서 기기 없이도 테스트 가능하게 만들고, JSON 문자열 바디가 가짜 transport에 숫자형 `files[0].file_size`를 가진 *객체*로 도착하는지 확인하는 테스트를 추가했습니다.

### 버그 2 — 응답 봉투, 그리고 항상 타임아웃 나던 폴 루프

요청을 고치니 다음 문제는 응답을 읽는 것이었습니다. 실제 `POST /file` 200 바디는 이렇게 생겼습니다:

```json
{
  "status": 200,
  "data": {
    "files": [
      {
        "file_id": "2cnJM/o4Ex…",
        "requests": [
          { "method": "PUT", "url": "https://…s3-accelerate.amazonaws.com/…", "headers": { "Content-Length": "131072", "Content-Type": "image/jpeg" } }
        ]
      }
    ]
  }
}
```

코드가 틀린 게 두 가지였습니다:

1. 모든 게 `{status, data: {…}}`로 감싸여 있습니다. 리더는 `body.result`와 `body.files`를 보고 있었기 때문에, 결국 `body` 자체로 떨어져서 아무것도 못 얻었습니다.
2. 업로드 URL은 `files[0].url`이 아니라 `files[0].requests[0].url`에 중첩돼 있습니다. 메소드와 presigned 헤더도 마찬가지입니다(이 헤더는 S3 서명이 커버하기 때문에, `PUT`이 그대로 글자 그대로 전달하지 않으면 403이 납니다).

같은 봉투 버그의 더 나쁜 사례는 폴 루프에 있었습니다. 폴 응답은 실제 상태를 `data.task_status`(`"running"` / `"success"` / `"error"`)에 담습니다. 코드는 최상위 `status` 필드를 읽고 있었는데 — 그건 HTTP스러운 `200`입니다 — 그러니 `"success"`도 `"error"`도 절대 매칭이 안 됐고, **폴 루프가 매 분석마다 120초 하드 타임아웃까지 끝까지 돌았습니다.**

수정은 작은 헬퍼 하나를 모든 리더에 적용한 것이었습니다:

```js
function unwrap(body) {
  return body?.data ?? body?.result ?? body ?? {};
}
```

여기에 목과 기존 픽스처가 여전히 파싱되도록 관대한 필드 폴백을 더했습니다.

### 버그 3 — `format: "json"`은 점수를 파일이 아니라 인라인으로 돌려줍니다

어댑터는 ZIP 모드 흐름에 맞춰 짜여 있었습니다. 끝날 때까지 폴하고, 별도의 `score_info.json`을 `GET`하고, 평평한 `{concern_id: {raw_score}}` 객체를 파싱하는 식이었죠. 그런데 `format: "json"`에서는 점수가 **폴 응답 안에 인라인으로** `data.results.output[]` 아래에 옵니다 — `{ type, ui_score, raw_score, mask_urls }`의 배열입니다. 가져올 두 번째 파일이 없습니다. 그래서 json 경로의 추가 다운로드를 삭제하고, 결과를 메트릭 id로 키를 잡아 인라인 배열에서 바로 만들었습니다. (`score_info.json` 리더는 폴백으로 남겨뒀습니다. 목 어댑터와 샘플 픽스처가 그 모양을 쓰거든요.)

### 버그 4 — 액션 이름 하나가 틀리면 태스크 전체가 400

태스크 요청은 `dst_actions`를 보냅니다 — 점수를 매길 피부 항목 목록입니다. 제 `metrics.config.js`는 id 15개를 담고 있었는데, 그중 몇 개는 추측이었습니다. 그중 하나가 `dark_circle`이었습니다. SD 티어의 실제 액션은 `dark_circle_v2`입니다(접미사 없는 `dark_circle`은... 그냥 유효한 SD 액션이 아닙니다). 그리고 모르는 액션은 그냥 건너뛰어지는 게 아니라 `InvalidParameters`를 돌려주고 **`POST /task/skin-analysis` 호출 전체를 실패시킵니다.** SD와 HD 액션 이름을 한 요청에 섞을 수도 없습니다.

이건 Perfect Corp 문서에서 공식 SD 액션 목록을 뽑아다가 코드가 보내는 것과 diff를 떠서 찾았습니다. 기록용으로, 유효한 SD 목록은 이렇습니다:

```
wrinkle, acne, pore, texture, moisture, firmness, redness, oiliness, radiance,
age_spot, dark_circle_v2, eye_bag, droopy_upper_eyelid, droopy_lower_eyelid,
tear_trough, skin_type
```

## 작업 구조가 버그 4를 어떻게 잡았나

프로세스에 대한 짧은 곁가지 이야기입니다. 버그 4가 출시로 안 나간 게 바로 이 구조 덕분이거든요.

skintrack은 자기 저장소가 있고, 그 안에 작은 팀(`project-lead` → `project-eng` → `release-check`)이 있습니다. 회사 세션은 설계와 검토를 하고, 저장소 팀이 브랜치에서 빌드합니다. "부서를 만들어놓고 정작 일은 자기가 한다"는 실패 패턴에 대해서는 전에 쓴 적이 있는데 — 이게 그 문제의 해법이고, 여기에 적용한 겁니다.

그래서 API 수정의 흐름은 이랬습니다. 제가 수정 브리프(버그 네 개, curl로 알아낸 것들, 각각에 대한 유지보수 가능한 수정 방향)를 써서 `v0.3-fixes` 브랜치로 저장소 팀에 넘기고, 돌아온 결과를 검토했습니다.

1라운드는 버그 1~3이 제대로 고쳐진 채로 돌아왔습니다. 테스트 80/80, 깨끗한 빌드, 자체 검토 PASS. 그런데 만들어낸 `dst_actions` 목록에는 여전히 `dark_circle`이 들어 있었고, 유효한 액션 세 개(`firmness`, `droopy_upper_eyelid`, `droopy_lower_eyelid`)를 이유 없이 빼먹었습니다. 이건 **검토에서 FAIL**입니다 — 틀린 문자열 하나가 모든 실제 태스크를 400 내니까요. 뭐가 잘못됐는지 정확히 적어서 돌려보냈고, 2라운드는 딱 그것만 고쳤습니다: 공식 SD 액션과 skintrack 자체 메트릭의 교집합인 14개 id 목록, 죽은 `dark_circle` 메트릭 행 제거, `dark_circle_v2`를 단일 "다크서클" 메트릭으로 리라벨. 테스트 81/81. 머지.

재시도 상한은 스펙상 빌드 2라운드까지입니다. 다른 건 두 번째 라운드가 필요 없었습니다.

## 이제 됩니다

머지 후에 폰에서 진짜 엔드-투-엔드 분석을 한 번 돌렸습니다: `/file` → S3 `PUT` → 태스크 생성 → 폴 → 인라인 점수. 셀카 한 장에서, 기기 위에서, 진짜 피부 점수가 나왔습니다.

(이미지-자리표시자: 결과 화면 — 항목별 점수 + 종합)

3~5단계는 curl로 탐침하지 않고 문서에 맞춰 코딩했습니다(태스크 생성은 유닛을 쓰고, 제 예산은 총 80~125회니까요). 그래서 첫 실제 실행이 곧 검증이었습니다. 잘 버텼습니다.

## 첫 도그푸딩 라운드 (v0.4a)

그다음 며칠 실제로 써봤더니, 새로운 문제 한 무더기가 나왔습니다. "분석이 틀렸다"는 건 하나도 없었습니다 — 전부 "이거 쓰면서 살기 짜증난다" 쪽이었습니다.

**여기저기 raw float.** 결과 화면에 `모공 50.28319990634918`이 떴습니다 — API에서 온 raw `raw_score` 그대로였죠. 응답은 사실 `raw_score`(float)와 `ui_score`(표시용으로 보정된 0~100 정수, 예: raw 57.33 → ui 68) 둘 다 담고 있습니다. `session.scores`가 `ui_score`를 저장하도록 바꾸고(없으면 `Math.round(raw_score)`로 폴백), 손대지 않은 원본 페이로드는 `session.raw`에 유지해서 잃는 게 없게 했고, 렌더 시점에 `Math.round()`를 걸어서 DB에 이미 들어있는 float 세션도 마이그레이션 없이 깔끔하게 표시되게 했습니다.

(이미지-자리표시자: raw float 버그 — "모공 50.28319990634918")

**카메라 촬영 후 로딩 화면 뜨기 전 약 5초 프리즈.** 무거운 픽셀 작업 전부 — 디코드, 풀 해상도 캔버스 그리기, 얼굴 폭 추정을 위한 픽셀 스캔, JPEG 재인코딩 — 이 앱이 화면을 이동하기 *전에* 메인 스레드에서 동기적으로 돌고 있었습니다. 방금 찍은 카메라 사진은 보통 갤러리에서 고른 것보다 훨씬 크기 때문에, 카메라 촬영일 때 더 심했습니다. 캡처 흐름을 다시 짰습니다: 네이티브 피커를 열고, raw 이미지를 넣어두고, 바로 화면을 이동해서 진행 바가 뜨게 한 다음, 조건화 작업을 로딩 화면의 첫 단계로 돌립니다.

**가끔 조용히 나던 캡처 실패.** 같은 원인입니다. RAM이 적은 기기에서는 큰 카메라 이미지로 `canvas.toBlob`이 `null`(메모리 부족)을 돌려줄 수 있고, 그러면 `blob.arrayBuffer()`가 throw하고, 에러는 놓치기 쉬운 작은 상태 div에 떨어졌습니다. 이제 조건화 실패는 타입이 있는 `CaptureError`를 던지고 "진단 보기" 버튼이 달린 전체 에러 카드에 떨어집니다. 여기에 이미지 크기와 타이밍을 기록하는 진단 단계를 더해서, 다음에 또 나면 스크린샷만으로 디버깅할 수 있게 했습니다.

**셀카가 거부됐을 때 안내가 없음.** 옆모습 사진을 찍었더니 분석이 거부했는데 어떻게 하라는 설명이 없었습니다. 그래서 v0.4a에 캡처 가이드 모달(정면, 프레임 채우기, 밝은 조명, 머리 뒤로)을 추가했습니다 — 첫 실행 때 한 번 보여주고, 홈 화면에서 언제든 다시 열 수 있고, 얼굴/조명 에러 카드에서 링크됩니다.

작은 것도 하나: 결과 사진이 이제 탭하면 확대되고(라이트박스), 이를 위해 앱이 살짝 큰 이미지(약 720px)를 저장합니다. 여전히 로컬 전용이고 "모든 데이터 삭제"로 같이 지워집니다.

## 다음 편

분석은 되고, 앱은 쓸 만합니다. 2편은 이걸 *제품*으로 어디까지 끌고 갈지에 대한 이야기입니다: 의도적으로 하루 한 번만 스캔하는 루프(피부 트래커에는 이게 딱 맞는 주기이기도 합니다), 나중에 있을 충전 흐름의 화폐가 될 귀여운 "콜라겐" 크레딧, 숨은 개발자 모드, 그리고 앱을 더 나쁘게 만들지 않으면서 광고나 제휴 링크가 들어갈 수 있는 자리. 그건 2편에서.
